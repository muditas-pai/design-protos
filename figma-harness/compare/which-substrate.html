Design harness · substrate decision

Where should the harness actually build?

The harness itself is settled. This is only about where the thing it produces lives: a React prototype we build ourselves, Figma, or a branch on the live product. Two of the three turn out to be worse versions of the third.

Written after building the React version far enough to judge it fairly, and testing what Figma can and cannot do. 30 Jul 2026.

What does not change

Step 0 and the gate · two isolated judges · adjudicate, the conflict rule, the pass budget · harvest and its routes · the day-1 assets. Four fifths of the harness is untouched in all three.
One option asks us to build the place designs are made. One uses the place designs are already made. One uses the product itself.

pitchdeckdoclist

Things engineering already maintains

  • No prototype at all. The screen judged is the screen shipped
  • Zero copies. One design system, the one that renders in production
  • About 10 live screens picked as canonical, out of 90 routes
  • Git is the isolation: one branch, one screen file, nothing added to main
  • It ends as a PR, so there is no handoff
Five things we get free

The point of the harness is that judgement piles up and the next run starts smarter. What stops a system like that is never the rate of learning, it is that upkeep eats the attention capture needed. Only the first option puts the substrate on our plate.

Read down the columns. The React prototype wins no row outright: everything it offers, pitchdeckdoclist does better or as well, and it carries costs neither other option has. Figma wins two rows, the lint and who can operate it, and loses the four that decide whether the output is real.

Why the React prototype is out

It was built far enough to judge, and it earns nothing that pitchdeckdoclist does not do better. Its three arguments were flows, reachability, and speed. The product has real flows and real click paths, and speed stopped mattering once runs became asynchronous. What it adds instead is a fourth copy of the design system, screens hand-ported from Figma that drift from both Figma and production, and an annotation tool written from scratch. Costs that compound, in exchange for nothing unique.

Why Figma is out too

This is the harder one, because Figma is genuinely cheaper to explore in and genuinely open to every designer. Three things outweigh that.

Two substrates is two of everything Two sets of anchors, two lints, two capture channels, two sets of rules to keep in step. Parallel systems drifting apart is the disease this whole harness exists to treat.
It reintroduces translation Exploring in Figma and converging in code means picking a frame and then rebuilding it. That is the re-implementation step the React prototype was criticised for, moved rather than removed.
It splits the corpus Annotations would accumulate against two different substrates, so counting recurrence, which is the entire promotion ladder, gets harder for no gain.

The node-tree lint was the strongest argument for Figma and it mattered less than it sounded. It only ever validated frames that then got rebuilt in code, so it checked a thing that was not the thing that ships.

The distinction that resolves it

Two different activities get called divergence.

Direction-finding "What if the whole thing were a feed." Wild, rough, mostly wrong, thrown away. Happens in Figma, on paper, wherever suits. It never enters the harness and never did.
Variation Four treatments of a settled direction. Tighter, closer to real, and the constraints matter. Code is arguably better here, because the constraints are real rather than drawn.

Dhruv's spec already puts the first outside the system: crazy8s feeds a pick into step 0. So the harness only ever sees the second kind, and that kind is sibling files on one branch.

Designers keep using Figma. It just stops being a harness substrate, with no anchors of its own, no lint, and nothing to keep in step.

Building on the product: what it solves

Three things neither alternative can.

No fidelity gapThe canonical screens are live pages. Nothing is ported, so nothing drifts, and no copy of the design system is created.
Don'ts for freeNinety routes of accreted product. The screens nobody has touched in a year are anti-patterns that already exist, anchored to real files. The empty-corpus problem on day 1 solves itself. (Worth confirming with git log rather than file dates.)
No handoffThe winning exploration is already production code in the production repo. There is no translation step where intent gets lost.

And what it costs

A variation is heavier to produce. Real props, real imports, real state, and the stack has to be running. Moving a rectangle is faster than editing a component.

The operator set narrows. React plus the ability to run three services, so fewer people can produce a variation. Rough exploration stays open to everyone because it happens outside the harness.

Reliability, not speed. Build time stops mattering if runs are asynchronous, but three services all have to be up. A run that dies twenty minutes in because one was down fails late, so preflight them.

The lint reads source. "Uses a real component" becomes an import check rather than a structural fact.

What it does not need

No seams, no override registry, none of the React prototype's machinery. Explorations never coexist in a build, so git is the isolation: one exploration branch holding eight sibling screen files, everything below them imported unchanged, a dev-only route to view them. Nothing is added to main and nothing lands on engineering's plate.

What is worth telling engineering, as a courtesy rather than a request: an agent will be creating branches under your name, exploration branches get deleted after a pick, and the PR that arrives is a design proposal rather than production-ready code.

Annotations have to be countable

Whichever substrate wins, this decides whether the loop works. The promotion ladder is entirely arithmetic: "this rule fired six times across three surfaces, promote it?" A folder of annotated screenshots cannot answer that. An image is not a corpus.

So the record is the source of truth and the images hang off it:

{
  "id": "2026-07-30-dashboard-004",
  "screen": "dashboard", "route": "/", "commit": "628d6f1",
  "at": { "selector": "…", "classes": ["nav-item"], "text": "Create project" },
  "verdict": "bad",
  "note": "PRO badge but the row stays fully enabled, so a free user
           only learns it is gated after clicking",
  "author": "mudita", "as_of": "2026-07-30",
  "images": { "element": "…", "context": "…", "page": "…" }
}

Three images per note, because they answer different questions: the element is what the claim is about, the context shows the relationship that makes it wrong, and the annotated page is the review view.

The important property is that the images are derived, not authored. Given a selector and a running app, all three regenerate automatically, so when a screen changes they can be re-derived and the diff shows exactly what moved underneath the annotation.

Agentation captures the right payload but does not persist or read it back, so relaying it depends on copying text over every time. The annotation layer already built for the React prototype does write structured records, and it does not need to stay a React component: as an injectable script it would run against pitchdeckdoclist with nothing added to that repo.

Where I land

One substrate: pitchdeckdoclist. Not because it is the pleasant option, it is the heaviest of the three to work in. Because it is the only one where the thing being judged is the thing that ships, and because a second substrate would cost a translation step, a split corpus and two of every asset, in exchange for exploration that is easier but does not enter the harness anyway.

The React prototype is dominated. Figma stays a design tool and stops being a harness substrate.

Confident about the maintenance and fidelity arguments: the four-copy problem, a 342k-line frontend with no isolated component dev, 90 routes, and a Figma lint that independently rediscovered two token gaps found by hand days earlier, are measured rather than argued.
Not confident about the practice: nothing has been generated in any substrate yet, the reliability of a three-service asynchronous run is untested, and the free-don'ts premise needs checking against git history rather than assumed.
Changed my mind twice writing this, first away from the React prototype and then away from Figma. Both times the argument that moved me was the same one: a copy you have to keep in step is a cost that grows, and a translation step is where intent gets lost. Weight the measured parts, not the recent ones.
