Design harness · substrate decision

Where should the harness actually build?

The harness design is settled and good. This is only about where the thing it produces lives: in a React prototype app we build ourselves, or in Figma.

Written after building the React version far enough to judge it fairly. Mudita + Claude, 30 Jul 2026.

Everything that stays the same

Both options run the identical harness. None of the thinking changes:

Step 0 and the gate. Turning a PRD into a numbered checklist you ratify before anything gets built.
Two judges, isolated. One on the picture, one on the requirements, neither seeing the other's findings.
Adjudicate. The merge, the conflict rule, the two-pass budget, the six halt verdicts.
Harvest. The closing question, the routes, one home per learning, you confirm every write.
The day-1 assets. content.md, requirements-template.md, exemplars.json, a lint.

Roughly four fifths is untouched. The argument below is entirely about the remaining fifth.

The difference in one line

One option asks us to build and maintain the place designs are made. The other uses the place designs are already being made. Everything else follows from that.

What each one asks you to keep alive

This is the part that is easy to underestimate, so here it is as a list rather than a paragraph.

A · baby-PAI

Things we would build, then have to keep working

  • A React app: 149 files, dependencies, a build, a dev server
  • A third copy of the design system. Production React, then pai.css, then the app's own wrappers. Each hand-synced from the one above
  • Canonical screens hand-ported from Figma, which will drift from both Figma and the live product
  • An annotation layer written from scratch, because a prototype repo has no critique lying around
  • A build committed or a deploy action, so anyone can see a link
Five things to maintain

B · Figma

Things that already exist and are maintained by someone else

  • No app, no build, no dev server. The artifact is a frame in a file designers already have open
  • One design system: the published library, tied to the real codebase by Code Connect
  • The screens are the screens. Nothing to port, nothing to drift
  • Critique already happens in Figma, and the edits designers make are themselves the feedback
  • A Figma link is a link
Four things we get for free

Why upkeep is the deciding factor

The point of the harness is not any one screen. It is that judgement piles up: rules, checks, anchors, checklist defaults. The next run starts smarter than the last.

What eventually stops a system like that is never the rate of learning. It is that the learning creates upkeep, upkeep eats attention, and attention is what capture needed in the first place.

So the question is which option puts less weight on that. In A, the rules and the substrate both live with us and compete for the same hours. In B, the substrate is maintained by designers doing their normal job.

How each one collects feedback

The loop only works if judgement gets captured. The two do this very differently.

 A · baby-PAIB · Figma
Where critique comes from An annotation tool we build, and someone has to remember to use it The edits you already make, plus corrections you already type
Coverage Patchy by nature. Nothing annotated reads as approved You cannot forget to correct the agent
Strongest way to lock a rule in A lint check. The components are not the real ones A component in the real library

That last row matters more than it looks. Once the only primary button in the library is navy, "navy is the action colour" stops being a rule anyone can break. It becomes the only thing you can build. No rule text achieves that.

What happens when nobody is looking

The real test is not how each behaves while we are paying attention. It is what they do during a busy month.

 After neglect
A · baby-PAI Dependencies age, the ported screens drift, the three design-system copies diverge, annotation stops. The app still runs perfectly. It has just quietly stopped representing the product, and now produces confident, wrong judgements.
B · Figma The file is still current, because designers kept using it for real work. The written rules go stale, which is equally true of A.

A fails in the dangerous direction: it becomes misleading without looking broken. B just gets out of date.

Who can actually use it

In A, the artifact is JSX. Changing it requires writing React, which most designers do not. A system built to capture designer judgement, whose output most designers cannot open and edit, has a problem that no amount of tooling fixes. It also means the system runs only while one specific person is available.

In B, the artifact is a Figma frame.

Where baby-PAI is genuinely better

Three real things, stated plainly rather than minimised.

Flows A running app carries state between steps. What you typed on step 1 is there on step 2. Figma frames cannot do this, so "what happens after the primary action" can be drawn but not walked. This is the only irreplaceable loss.
Reachability The harness currently proves an entry point exists by having the renderer click through to it. You cannot click a frame, so that check weakens to prototype links or a judge's guess.
Speed and control A 700ms local build beats round trips to Figma, and something we own end to end is easier to measure and debug.

The asymmetry that decides it

A's costs get worse every month. B's costs are the same size in a year as they are today. Three copies of the design system drift further every week. Ported screens fall further behind with every Figma edit. Meanwhile "a frame is not a flow" is exactly as true next year as it is now, and no worse.

A system whose overhead grows alongside its knowledge never reaches the point the knowledge was for.

Where I land

Figma. Not because it produces better designs, it does not. Beauty and brand alignment come from good anchors and a good judge, and those are identical in both. Figma wins because the same harness costs far less to keep alive, collects its feedback without anyone remembering to, fails safely when ignored, and can be operated by every designer rather than one.

High confidence
The maintenance argument. The three-copy problem, the 342k-line frontend with no isolated component dev, and a Figma lint that independently rediscovered two token gaps found by hand days earlier, are all measured rather than argued.
Low confidence
The practical side. No design has been generated in Figma yet, its speed across a full run is unmeasured, and the flow gap has not been tested against a real PRD.
Worth discounting
The React version was built first and then argued against. Weight the measured parts, not the recent ones.

What matters more than this choice

Neither option has a way to tell whether the accumulated rules are actually helping. Vercel's version of this runs the agent both with and without its guidance and compares, and holds back test cases to check the rules generalise. Without something like that, both architectures pile up confident nonsense at exactly the same rate.

And the one real harness run so far ended at checklist-bug, which is a step-0 failure: turning the PRD into a ratifiable checklist. That step is identical in both options and is where the only hard evidence points. It is worth fixing before the substrate question is settled at all.

Both harnesses are drawn at matching detail, with the substrate layer and its costs made explicit in each, so they can be read side by side.
