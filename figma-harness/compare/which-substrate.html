Design harness · substrate decision

Where should the harness actually build?

The harness itself is settled. This is only about where the thing it produces lives: a React prototype we build ourselves, Figma, or a branch on the live product.

Written after building the React version far enough to judge it fairly, and testing what Figma can and cannot do. 30 Jul 2026.

What does not change

Step 0 and the gate · two isolated judges · adjudicate, the conflict rule, the pass budget · harvest and its routes · the day-1 assets. Four fifths of the harness is untouched in all three.
One option asks us to build the place designs are made. One uses the place designs are already made. One uses the product itself.

pitchdeckdoclist

Things engineering already maintains

  • No prototype at all. The screen judged is the screen shipped
  • Zero copies. One design system, the one that renders in production
  • About 10 live screens picked as canonical, out of 90 routes
  • Git is the isolation: one branch, one screen file, nothing added to main
  • It ends as a PR, so there is no handoff
Five things we get free

The point of the harness is that judgement piles up and the next run starts smarter. What stops a system like that is never the rate of learning, it is that upkeep eats the attention capture needed. Only the first option puts the substrate on our plate.

Building on the product: what it solves

Three things the other two cannot.

No fidelity gapThe canonical screens are live pages. Nothing is ported, so nothing drifts, and no copy of the design system is created.
Don'ts for freeNinety routes of accreted product. The screens nobody has touched in a year are anti-patterns that already exist, anchored to real files. The empty-corpus problem on day 1 solves itself. (Worth confirming with git log rather than file dates.)
No handoffThe winning exploration is already production code in the production repo. There is no translation step where intent gets lost.

And what it costs

Divergence gets expensive. Eight variations means eight branches and eight checkouts, with no way to see them side by side. crazy8s does not really work here.

The operator set narrows. React plus the ability to run three services. Fewer people can drive it than either alternative.

Reliability, not speed. Build time stops mattering if the harness runs asynchronously, but three services all have to be up. A run that dies twenty minutes in because one was down fails late, so preflight them.

The lint weakens. Back to reading source, where "uses a real component" is an import check rather than a structural fact. That is the one thing the Figma node tree did better.

What it does not need

No seams, no override registry, none of the machinery the React prototype required. Explorations never coexist in a build, so git already provides the isolation: one branch, one duplicated screen file, everything below it imported unchanged. Nothing is added to main and nothing lands on engineering's plate.

What is worth telling engineering, as a courtesy rather than a request: an agent will be creating branches under your name, exploration branches get deleted after a pick, and the PR that arrives is a design proposal rather than production-ready code.

Annotations have to be countable

Whichever substrate wins, this decides whether the loop works. The promotion ladder is entirely arithmetic: "this rule fired six times across three surfaces, promote it?" A folder of annotated screenshots cannot answer that. An image is not a corpus.

So the record is the source of truth and the images hang off it:

{
  "id": "2026-07-30-dashboard-004",
  "screen": "dashboard", "route": "/", "commit": "628d6f1",
  "at": { "selector": "…", "classes": ["nav-item"], "text": "Create project" },
  "verdict": "bad",
  "note": "PRO badge but the row stays fully enabled, so a free user
           only learns it is gated after clicking",
  "author": "mudita", "as_of": "2026-07-30",
  "images": { "element": "…", "context": "…", "page": "…" }
}

Three images per note, because they answer different questions: the element is what the claim is about, the context shows the relationship that makes it wrong, and the annotated page is the review view.

The important property is that the images are derived, not authored. Given a selector and a running app, all three regenerate automatically, so when a screen changes they can be re-derived and the diff shows exactly what moved underneath the annotation.

Agentation captures the right payload but does not persist or read it back, so relaying it depends on copying text over every time. The annotation layer already built for the React prototype does write structured records, and it does not need to stay a React component: as an injectable script it would run against pitchdeckdoclist with nothing added to that repo.

Where I land

Split it by phase, and drop the React prototype.

Diverge in Figma. Cheap, no stack, every designer can do it, and eight variations side by side is native. This is where taste gets explored and most work gets thrown away.

Converge in pitchdeckdoclist. Real components, real flows, verifiable reachability, and it ends as a PR. This is where the expensive machinery earns its keep.

Dhruv's spec already draws this line. For crazy8s it says the rendered checks and the judges run only on the pick. The heavy apparatus was never meant to run on all eight, and that is exactly the seam between the two substrates.

Confident about the maintenance and fidelity arguments: the four-copy problem, a 342k-line frontend with no isolated component dev, 90 routes, and a Figma lint that independently rediscovered two token gaps found by hand days earlier, are measured rather than argued.
Not confident about the practice: nothing has been generated in either substrate yet, the reliability of a three-service async run is untested, and the free-don'ts premise needs checking against git history rather than assumed.
Discount the fact that the React version was built first and then argued against. Weight the measured parts, not the recent ones.

What matters more than this choice

Neither remaining option can tell whether its accumulated rules actually help. Without running the agent both with and without its guidance and comparing, all three pile up confident nonsense at the same rate. And the one real harness run so far died at step 0, turning the PRD into a ratifiable checklist, which is identical in every option here.
