Websites and apps

How websites and apps sit next to decks, how people make them, and what they need beyond the page itself. Written for people who make decks, not for developers.

1How to think about it

Three things you can make. What separates them is what the other person does with it, not the technology.

Deck you present it

Slides, in order. You're in the room, or you send it.

Pitch, QBR, weekly update
Website people visit it

Pages people read on their own, with a link to share. Can collect sign-ups.

Launch page, waitlist, event, portfolio
App people use it

Something people do, not just read. It remembers things: bookings, orders, answers.

Booking form, product quiz, pricing calculator, team tracker
RecommendationDon't call it a CMS, and don't make people pick a type up front. People describe what they want ("a page for the Orbit launch with a waitlist") and we decide: if it only shows things and collects sign-ups, it's a website. If people log things, look things up or come back to it, it's an app. The line is fuzzy on purpose; a website that grows a booking form is still the same project.

The mental model to repeat everywhere: it's made like a deck, edited like a deck, and shared with a link. Everything technical (hosting, the database, code) is ours to worry about.

Deck
  • Blue type badge
  • Cover fills the thumbnail, edge to edge
  • Meta: when it was edited
Website
  • Green type badge
  • Top of the page inside a small browser window, address showing
  • Live or Draft tag on the thumbnail
  • Meta: the one number that matters (sign-ups or visits); the address is in the thumbnail
App
  • Purple type badge
  • A phone-sized screen plus the app's icon, so it reads as something you use
  • Live or Draft tag
  • Meta: new activity (answers, bookings, orders)

The badge is the fast read when scanning; the frame confirms it. The same three badges appear in the type tabs, the New menu, search results and the editor's top bar, so each type keeps one colour everywhere. Clicking a website or app opens its editor, same as a deck. The menu adds Open live site and Copy link. The thumbnail updates on publish, not on every edit, so it always shows what visitors see.

RecommendationQuestion 2 ("what do you want to keep?") is where data gets set up, without anyone saying database. If they pick "their email", we create a Sign-ups list behind the scenes. That one answer decides most of the setup.

4Editing

Same three ways people already edit decks. No code view in the main path.

Click and type

Click any text, image or button on the page and change it in place. Covers most edits.

Ask

"Add a section with customer reviews", "make the form also ask for their cat's name". The chat changes the page and the data together.

Sections

Pages are made of sections the way decks are made of slides: reorder, duplicate, delete, add from a short list.

Every publish saves a version, so people can undo a bad change on a live site. Code view can exist later for power users, behind a menu, never on the main path.

5Data, not a database

Most websites only need a list of form replies. Apps need a few tables. Either way, people see something like a spreadsheet tab, named after what's in it.

Website

Responses: one list per form. Name, email, when.

  • Email me when someone signs up
  • Download as a spreadsheet
  • Send each one to HubSpot, Klaviyo or Google Sheets (the connectors we already have)
App

Data tab: a few named lists, like Bookings, Products, Customers.

  • Created by the AI from what the app needs; renamed or extended by asking
  • Rows can be edited by hand, like a sheet
  • Can read from connected apps: a stock checker that reads Shopify, a dashboard that reads Google Analytics

Words to use

Database, table, schema
Data, or the list's own name (Sign-ups, Bookings)
Record, row, entry
Response, booking, order: whatever it is
CMS, collection
"Products" or "Posts", shown as a list you can edit
Deploy, host, build
Publish
Auth, user accounts
"Who can use it": anyone, people with the password, or people you invite
Environment, staging
Draft and Live
Is it a CMS?Partly, and only when the content repeats. A site with a product grid or a blog gets a Products or Posts list in the Data tab, and the page updates when the list does. That's the CMS, without the word. Everything else is edited on the page itself.

Other examples: an RSVP to an event page, a question from a contact form, the answers to the bed finder quiz, a booking for a showroom visit. Decks never have responses; websites and apps do whenever they have a form.

Where they show

On the tile

"212 sign-ups this week" under the title, so the dashboard shows which site is working.

Inside the site

A Responses tab next to Edit and Settings: the list, a download button, and "email me for each one".

Dashboard tabs

The type tabs (All, Decks, Websites, Apps) filter the grid. A separate Responses tab on the dashboard only makes sense once people run several sites; later, not first.

8Phone apps

Apps need to live on a phone, not only open in a browser. Two steps, the first much cheaper than the second.

NextAdd to home screen

Visitors open the link on their phone and add the app to their home screen. It gets its own icon, opens full screen with no browser bar, and can send notifications.

No app store, no review. Works on iPhone and Android. The app is built for phones from the start, so this is mostly settings.

LaterIn the App Store and Google Play

We wrap the same app and submit it to the stores under the customer's name, so people can search for it and install it.

Needs the customer's own developer accounts, store screenshots and a description (we can generate those), and passing Apple and Google's review. A paid-plan feature.

What this adds: apps edit in a phone frame by default (websites in a desktop frame), and Settings gains app icon, name on the home screen, launch screen colour and notifications. All four are made from the brand kit unless changed.
